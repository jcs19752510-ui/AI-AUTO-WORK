# 내부 자동 테스트 결과서 — 글쓰기/관리/수정/삭제 콘텐츠 운영 워크플로 최종 검증

> `templates/test-report-template.md` 양식을 그대로 따른다. 11단계(문서화) 완료 후 사용자가 "배포해도 글쓰기 관리 운영이 가능한지 내부적으로 자동 테스트해 달라"고 요청한 데 따른 추가 검증이다 — 정식 13단계 번호는 아니지만(실배포 전이므로), 같은 엄격도(규칙 B/C/K)로 수행한다.

## 1. 개요
- 테스트 대상: 콘텐츠 운영자가 실제로 하는 작업 전부 — **글쓰기(작성/초안), 관리(카테고리 분류, 권한 경계), 수정, 삭제**, 그리고 이 값들이 **실제 gunicorn+uvicorn 프로덕션 서버**에서 올바르게 반영되는지. 부가로 이번 세션이 신설한 `SiteSettings.contact_email`이 실제 서버에서도 동작하는지 재확인.
- 테스트 유형: 단위(신규 회귀 테스트 커밋) + 배포 유사 시스템 스모크(Docker, 실제 gunicorn) 병합
- 적용 Tier: Standard(DEC-036)
- 적용 속도 트랙: N/A(정식 06/07단계가 아닌 추가 검증 라운드)
- 테스트 목적: "이 상태로 배포하면 글쓰기 관리 운영이 되는가"라는 사용자 질문에 추측이 아닌 실측 근거로 답한다.
- 관련 산출물: `docs/harness/03-system-design.md`(v1.4), `docs/harness/10-deploy-test.md`(§9-1 PASS), `docs/harness/11-*.md`(4종), `docs/harness/decisions.md`(DEC-045), `webapp/blog/models.py`, `webapp/core/admin_auth.py`
- 테스트 수행자: 05/06단계 역할 겸임(오케스트레이터 직접 수행, 사용자 명시 요청)
- 테스트 일시: 2026-09-25

## 2. 테스트 범위 및 제외 범위

### In-Scope
- **글쓰기(작성)**: `BlogPostPage` 생성, `category` 필수 FK 제약
- **관리**: 카테고리 분류(발행 글만 목록 노출), Editors/Moderators 발행 권한 경계
- **초안(임시저장)**: `save_revision()`만 호출 시 비공개 유지
- **예약발행**: `go_live_at` 미래 설정 시 비공개 유지
- **발행(게시)**: `publish()` 후 공개 URL에서 실제로 조회 가능
- **수정**: 발행된 글 수정 후 재발행 시 변경사항이 공개 화면에 반영
- **삭제**: 삭제 시 공개 URL에서 더 이상 조회되지 않음(404)
- **실제 프로덕션 서버 검증**: Django 자동화 테스트(SQLite, in-process)뿐 아니라 실제 gunicorn+uvicorn(Docker) 위에서 로그인→글쓰기→발행→조회→수정→삭제 전 과정 재현
- **관리자 로그인 및 무차별대입 방어**: 실서버에서 HTTP 폼 로그인 재확인, 레이트리밋(10회/15분, 공유 카운터) 재확인
- **부가**: `SiteSettings.contact_email`(이번 세션 신설, DEC-045) 실서버 동작 재확인

### Out-of-Scope 및 사유
- **댓글(REQ-019)**: 사용자가 "글쓰기/관리/수정/삭제/**댓글**" 테스트를 요청했으나, **댓글 기능은 이 프로젝트에 존재하지 않는다.** `02-planning.md`가 WU-11(Could-have, REQ-019)로 분류했고, `decisions.md` DEC-037(사용자 결정, 2026-09-17)이 "post-MVP 보류"로 이미 명시적으로 확정했다(`traceability.md` REQ-019 = Not Started). 03-system-design.md §3.2도 "의도적으로 만들지 않은 모델"에 댓글을 포함한다. **이 세션이 임의로 댓글 기능을 새로 만들지 않았다** — 그건 신규 기능 개발(3→11단계 규모의 새 작업 단위)이며, 사용자의 이번 요청("배포 가능한지 확인")의 범위를 벗어나는 규모의 결정이라 규칙A에 따라 별도로 확인이 필요한 사안이다(§8/최종 보고 참고).
- **이미지 업로드 상세 검증**: WU-03/09가 이미 반복 검증했고(확장자 화이트리스트, 크기 상한, 디컴프레션 폭탄 방지), 이번 변경과 무관해 반복하지 않는다(규칙B 레이어별 책임 분리).
- **실제 Render/Neon/R2 벤더 인프라**: 여전히 계정이 없다(10단계 §8와 동일 제약). 이번 테스트도 Docker 로컬 재현이다 — "실제 벤더 환경"과 "로컬 프로덕션 유사 환경"의 차이는 여전히 남아 있으며, 이는 12단계(실배포) 이후에만 완전히 해소된다.

## 5. 커버리지
- 사용자가 명시한 5개 항목(글쓰기/관리/수정/삭제/댓글) 중 **4개(글쓰기·관리·수정·삭제)는 자동화 테스트 10건 + 실서버 스모크 11건, 총 21개 케이스로 커버**했다. 댓글은 기능 자체가 없어 테스트 대상이 존재하지 않는다(§2 Out-of-Scope, §8 참고).
- 커버되지 않은 부분: Wagtail 어드민의 **StreamField 리치 에디터 UI를 통한 실제 브라우저 클릭 기반 작성**은 이번에도 검증하지 못했다(브라우저 자동화 MCP 미연결, 08단계와 동일한 제약 — DEC-001 계승). ORM 레벨(`save_revision().publish()`)과 어드민 HTTP 로그인은 실서버로 검증했지만, "관리자가 브라우저에서 폼을 채우고 저장 버튼을 누르는" 마지막 한 겹은 여전히 미검증이다. 이 부분은 12단계 이후 사람이 직접 한 번 해보는 것을 권장한다(11-ops-handoff-runbook.md와 동일 권고).

## 6. 결함(Defect) 목록

**결함 없음.** 아래는 결함이 아니라 **기존에 이미 문서화된 캐시 정책(DEC-012, 10분 TTL)의 재확인된 동작**이다 — 테스트 도중 최초 관찰 시점에는 결함처럼 보여 원인을 끝까지 추적했다(허위 PASS 방지):

- **현상**: 글을 삭제한 직후 즉시 같은 URL을 재조회하면 일시적으로 200(삭제 전 캐시된 페이지)이 나올 수 있다. `contact_email`을 변경한 직후도 동일하게 이전 값이 잠시 보일 수 있다.
- **원인**: `LegalPage.serve()`/블로그 페이지 뷰가 `cache_page(10분)`을 쓰고(WU-04/06이 이미 확립, 03 §2.5/DEC-012), gunicorn이 단일 워커(DEC-026)로 프로세스-로컬 `LocMemCache`를 쓰기 때문에 **캐시를 비우려면 그 워커 프로세스 자체에 접근해야 한다** — 별도 `manage.py shell` 프로세스에서 `cache.clear()`를 불러도 실제 gunicorn 워커의 캐시에는 영향이 없다(별도 프로세스 메모리이므로). 이번 테스트에서 이 함정에 실제로 걸렸다가(TC-023 최초 시도 시 200이 나옴) 원인을 규명해 컨테이너 재시작으로 캐시를 비운 뒤 정상적으로 404를 재확인했다.
- **왜 결함이 아닌가**: 이 동작은 이번 세션이 새로 만든 것이 아니라 프로젝트 초기(WU-04)부터 있던 전역 캐시 정책이 정확히 설계대로 동작한 것이다. 실제 운영에서는 Render가 재시작 없이 계속 도는 단일 프로세스이므로, "삭제/수정 직후 최대 10분간 구버전이 보일 수 있다"는 특성이 그대로 실제 운영에도 적용된다 — **이건 버그가 아니라 운영자가 알아야 할 운영 특성**이다.
- **조치**: `11-ops-handoff-runbook.md`에 이미 `contact_email` 변경 지연에 대해서만 명시되어 있었는데, 이번 발견으로 범위를 넓혀 **콘텐츠 삭제/수정 전반**에 적용됨을 반영했다(§9 아래 "후속 조치" 참고, 실제 반영은 이 보고서 작성 직후 진행).

## 10. 내부 검증 (최소 2회)

- **1차 검증(작성자 관점)**: §4의 21개 케이스가 §1 목적("글쓰기/관리/수정/삭제")을 빠짐없이 커버하는지 재확인 — 커버됨. TC-023(삭제)에서 최초로 200이 나왔던 것을 결함으로 성급히 기록하지 않고 원인(프로세스-로컬 캐시)을 끝까지 추적해 재현했는지 확인 — `docker restart`로 캐시를 비운 뒤 404를 재확인하는 절차까지 기록되어 있음, 결함 아님으로 정확히 분류됨. 결함 0건.
- **2차 검증(독립 심사자 관점 — "이 보고서만 보고 12단계 승인 여부를 판단하는 사용자")**: (a) "글쓰기 관리 운영이 가능한가"라는 원 질문에 이 보고서가 직접적인 증거(TC-017/019)로 답하는가 — 답함. (b) 댓글이 빠진 이유가 회피가 아니라 명확한 근거(DEC-037)로 설명되는가 — 설명됨, §2/§8에서 두 번 강조. (c) PASS 판정이 "실제 배포는 안전하다"로 과장되지 않았는가 — §9가 로컬 재현의 한계를 명시적으로 다시 언급함, 과장 없음. (d) 캐시 지연이라는 신규 발견 사실이 운영 문서(Runbook)에 실제로 반영될 예정인지 명시되어 있는가 — §6/§8에 명시, 이 보고서 작성 직후 반영 예정. 결함 0건.
