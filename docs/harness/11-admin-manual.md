## 1. 관리자 권한 체계와 역할별 접근 범위

이 서비스는 1인/소규모 운영을 전제로 설계되었다(`03-system-design.md` §5.1, DEC-009). 관리자 진입점은 **정확히 2개**이며, 둘 다 **동일한 `auth_user` 슈퍼유저 계정을 공유**한다. 이 사실은 이 문서 전체에서 반복해서 중요하므로 먼저 명확히 이해해야 한다.

| 진입점 | URL | 용도 | 비고 |
|---|---|---|---|
| Wagtail 관리자 | `https://<도메인>/cms-admin/login/` | 콘텐츠(블로그 글/카테고리/태그/이미지) 작성·발행·권한 관리 — **이 서비스의 실질적인 운영 화면** | 기본 경로 `/admin/`이 아니라 `/cms-admin/`으로 변경되어 있다(자동화된 스캐너 노출 감소 목적, §4 참고) |
| Django 기본 관리자 | `https://<도메인>/django-admin/login/` | **뉴스레터 구독자 목록 조회 및 하드 삭제(개인정보 파기절차) 전용** | 이 화면에는 콘텐츠 관리 기능이 없다. 콘텐츠 작업을 하려고 이 경로에 로그인할 필요는 없다 |

### 1.1 역할(그룹)별 권한

Wagtail 표준 그룹(Editors/Moderators)을 그대로 사용하며, 커스텀 그룹을 신설하지 않았다(DEC-009). 1인 운영 시에는 슈퍼유저 1명만 존재하는 것이 기본 전제이며, 추가 편집자가 필요해지면 Wagtail 어드민(설정 → 그룹)에서 아래 중 하나에 배정한다.

| 그룹 | 페이지(블로그 글) 권한 | 카테고리(Category 스니펫) 권한 | 이미지 권한 |
|---|---|---|---|
| Editors | 추가/수정 가능. **발행 권한 없음** — 작성한 글은 Moderators의 승인(발행)을 거쳐야 실제로 공개된다 | 추가/수정/삭제 가능 | 추가/수정 가능 |
| Moderators | 추가/수정/**발행** 가능 | 추가/수정/삭제 가능 | 추가/수정 가능 |
| 슈퍼유저 | 위 제한 없이 전체 | 전체 | 전체 |

- 페이지 권한은 Wagtail 코어가 루트 페이지에 부여하면 홈/블로그 글/법적 페이지 트리 전체에 자동 상속된다(Wagtail 표준 동작).
- 카테고리 스니펫 권한은 이 프로젝트가 마이그레이션(`core/migrations/0001_setup_editor_permissions.py`)으로 명시적으로 Editors/Moderators에 부여한 것이다. 이 마이그레이션이 실제로 적용되어 있지 않으면(예: 아주 오래된 배포본 복구 등) 슈퍼유저가 아닌 편집자는 카테고리를 추가/수정/삭제할 수 없다 — 그런 증상이 보이면 §5(이상 동작 발견 시 대응)를 참고해 기술 담당자에게 마이그레이션 적용 여부 확인을 요청한다.
- 이미지 권한은 Wagtail 자체 마이그레이션이 기본 부여하므로 별도 설정이 필요 없다.
- **2단계 인증(2FA)은 이 서비스에 구현되어 있지 않다.** 설계 단계(`03-system-design.md` §5.1)에서 v1 범위 밖으로 의도적으로 제외되었고, 향후 검토 대상으로만 기록되어 있다. 즉 계정 비밀번호가 유일한 인증 요소이므로 §3(비밀번호 관리)를 반드시 지킨다.
- **뉴스레터 구독자 관리(`/django-admin/`)에는 별도 그룹 권한 체계가 없다** — 이 화면은 슈퍼유저만 접근하도록 운영하는 것을 권장한다(구독자 개인정보 파기는 슈퍼유저 1인이 책임지고 수행하는 작업으로 설계되었다).

### 1.2 로그인 방법

1. `https://<도메인>/cms-admin/login/`에서 콘텐츠 관리자 계정으로 로그인한다. 콘텐츠 작업(글 작성/발행/카테고리 관리)은 전부 이 화면에서 이루어진다.
2. 뉴스레터 구독자 목록을 확인하거나 삭제해야 할 때만 `https://<도메인>/django-admin/login/`으로 별도 로그인한다. 두 로그인 화면은 같은 계정(아이디/비밀번호)을 쓰지만, 세션은 각 화면마다 별도로 로그인해야 한다(Wagtail 세션이 Django 기본 관리자 세션을 자동으로 대신해주지 않는다).
3. 최초 계정 발급(슈퍼유저 생성)과 비밀번호 재설정 절차 자체는 서버 배포/환경변수 조작이 필요한 운영 작업이므로 이 문서가 아니라 `docs/harness/11-ops-handoff-runbook.md`(운영 인수인계 문서)와 `webapp/ADMIN_ACCESS_GUIDE.md`를 참고한다. 이미 발급된 계정으로 일상 업무를 수행하는 것이 이 문서의 범위다.

## 2. 관리 기능별 사용법

### 2.1 블로그 글 작성 · 임시저장 · 예약발행 · 리비전(이력) 관리

`/cms-admin/`에 로그인한 뒤:

1. **위치 확인**: 페이지 트리에서 "블로그 인덱스" 하위에 신규 게시물을 만든다(홈 화면 하위 트리 어디든 자유롭게 만드는 구조가 아니라, 반드시 블로그 인덱스 아래에 위치해야 목록/RSS/사이트맵에 정상적으로 반영된다).
2. **작성**: 제목, 본문(문단/이미지/인용/FAQ 블록으로 구성되는 스트림필드), 카테고리(필수, 단일 선택), 태그(자유 입력, 복수 가능), 대표 이미지를 입력하고 "임시저장"한다. 임시저장 상태(`live=False`)에서는 방문자에게 절대 노출되지 않는다 — `/blog/<slug>/`로 직접 접근해도 404가 반환된다.
3. **미리보기**: Wagtail 기본 Preview 기능으로 실제 게시 전 화면을 확인할 수 있다. 미리보기는 방문자 노출과 무관하다.
4. **발행 방식 선택**(둘 중 하나):
   - **즉시 게시**: 저장 시 "게시" 옵션을 선택하면 바로 `live=True`가 되어 홈/목록/카테고리/태그/RSS/사이트맵에 즉시 반영된다.
   - **예약발행**: `go_live_at`(공개 시작 시각)과 필요 시 `expire_at`(공개 종료 시각)을 입력한다. `go_live_at`이 미래 시각이면 그 시각이 될 때까지는 비공개(404) 상태로 유지되다가, 시각이 도달하면 자동으로 공개된다. `expire_at`을 지나면 다시 자동으로 비공개(404) 처리된다 — Wagtail 표준 기능이며 별도의 수동 작업(발행 취소 등)이 필요 없다.
5. **리비전(이력) 관리**: 발행 이후에도 수정할 때마다 이전 버전이 리비전 이력에 자동으로 남는다. 실수로 잘못된 내용을 게시했을 때는 리비전 이력 화면에서 이전 버전과 비교하고 복원할 수 있다(Wagtail 기본 기능, 별도 백업 절차 불필요).

**게시 상태와 프런트엔드 노출 대응표** (헷갈리기 쉬운 부분이므로 반드시 숙지):

| Wagtail 상태 | 방문자에게 보이는가 |
|---|---|
| 임시저장(초안, `live=False`) | 아니오 — 404 |
| 예약발행 대기(`go_live_at`이 미래) | 아니오 — 404 |
| 게시됨(`live=True`, `go_live_at` 도달) | 예 — 목록/상세/RSS/사이트맵 전부 노출 |
| 만료(`expire_at` 경과) | 아니오 — 404(자동, 조치 불필요) |

이 워크플로는 `08-full-system-test.md` §4-4(E2E-O01~O03)와 `04-ux-design.md` §1.2에서 실제 동작이 확인되었다.

**Editors 그룹으로 로그인한 경우 주의**: "발행" 버튼이 보이지 않거나 눌러도 실제로 공개되지 않을 수 있다. 이는 오류가 아니라 의도된 권한 구조다(§1.1) — Editors가 작성한 글은 Moderators 권한을 가진 계정(또는 슈퍼유저)이 별도로 발행해야 공개된다.

### 2.2 카테고리 관리

- 카테고리는 Wagtail 어드민의 스니펫 메뉴에서 CRUD(생성/조회/수정/삭제)한다.
- 이 서비스는 콘텐츠 주제를 "운영자가 사전에 허용한 카테고리로만" 제한하는 운영 정책(REQ-015, 금융/의료/법률/보험 등 전문 인허가가 필요한 주제를 다루지 않겠다는 정책)을 카테고리 생성 권한을 통해 실행한다. 즉 **새 카테고리를 함부로 늘리는 것은 단순 분류 편의의 문제가 아니라, 이 서비스가 어떤 주제까지 다룰 수 있는지를 결정하는 정책적 행위**임을 인지하고, 신규 카테고리 추가 전에는 그 주제가 전문 인허가 영역(금융/투자, 의료/건강, 법률, 보험)에 해당하지 않는지 먼저 확인한다.
- **카테고리는 게시물의 필수 항목이며, 이미 게시물이 참조 중인 카테고리는 삭제할 수 없다**(`webapp/blog/models.py`, `category` 필드가 `on_delete=PROTECT`로 설정되어 있음을 코드로 확인). 삭제를 시도하면 Wagtail이 오류를 보여주고 삭제가 거부되므로, "실수로 지웠는데 관련 글이 전부 카테고리를 잃어버리는" 사고는 구조적으로 발생하지 않는다. 해당 카테고리를 정말로 없애려면, 먼저 그 카테고리를 쓰는 모든 게시물의 카테고리를 다른 값으로 변경한 뒤에 삭제해야 한다.

### 2.3 태그 관리

- 태그는 게시물 작성 화면에서 자유 입력으로 추가한다. 별도의 태그 관리 화면 CRUD는 이 프로젝트 범위에서 핵심 기능으로 설계되지 않았으며, 게시물 작성 시 자연스럽게 생성/재사용된다.

### 2.4 사용량 대시보드 확인 (`/cms-admin/usage/`)

- Render 무료 티어(월 750 인스턴스시간)와 Neon 무료 티어(월 100 CU-hour, 저장용량 0.5GB) 사용량이 한도에 가까워지고 있는지 참고하는 화면이다(`08-full-system-test.md` E2E-O04로 200 응답 확인).
- 이 화면은 참고 지표이며, 실제 유료 전환 여부 판단이나 플랫폼 청구/한도 상세 확인은 Render/Neon 각 벤더 대시보드가 기준이다. 유료 전환 판단 기준과 절차는 운영 인수인계 문서(`docs/harness/11-ops-handoff-runbook.md`)를 참고한다 — 이 항목은 콘텐츠 관리자의 일상 업무가 아니라 운영자(인프라 책임자)의 판단 영역이다.

### 2.5 뉴스레터 구독자 목록 조회 및 관리

`/django-admin/`에 로그인한 뒤 "Newsletter Subscribers"(뉴스레터 구독자) 항목으로 이동한다.

- **조회/검색**: 이메일, 상태(구독중/구독취소), 동의 시각, 마스킹된 접속 IP, 생성일을 목록에서 확인하고 이메일로 검색할 수 있다.
- **수정은 불가능하다(설계상 의도된 제한)**: 이 화면은 값 수정 기능이 없다(`has_change_permission`이 항상 `False`). 동의 시각/동의 버전/IP 등은 구독 시점에 시스템이 자동으로 기록한 "처리 근거 데이터"이므로, 관리자가 임의로 고쳐 쓰면 개인정보 처리 근거의 추적성이 깨진다. 값이 잘못 기록된 것처럼 보여도 이 화면에서 직접 고치지 않는다 — 기술 담당자에게 문의한다.
- **신규 추가도 불가능하다**(`has_add_permission`이 항상 `False`) — 구독자는 반드시 공개 구독 폼(`/newsletter/subscribe/`)을 통해서만 생성된다.
- **`status`(구독중/구독취소) 필드에 대한 중요한 주의**: 이 필드는 향후 기능(발송 인프라 추가 시 원클릭 구독취소)을 대비해 미리 만들어 둔 필드이며, **v1에서는 이 값이 자동으로 "구독취소"로 바뀌는 경로가 전혀 없다.** 즉 목록에 "구독중"이라고 표시되어 있어도 그것이 "본인이 여전히 수신을 원한다"는 것을 보장하지 않으며, 이 상태값을 구독자 삭제 여부 판단의 근거로 삼지 않는다 — 실제 삭제 여부는 아래 §3의 탈퇴 요청 절차만을 근거로 판단한다.

### 2.6 댓글 모더레이션 (REQ-019, 2026-09-25 추가)

이 사이트의 댓글은 **사전 승인제**다 — 방문자가 작성한 댓글은 운영자가 승인하기 전까지 공개 화면에 전혀 노출되지 않는다(`decisions.md` DEC-047 사용자 결정).

- **위치**: `/cms-admin/snippets/comments/comment/` (Wagtail 어드민 좌측 메뉴 "댓글"). Wagtail 콘텐츠 스니펫으로 등록되어 있어 블로그 글 작성과 같은 화면 체계 안에 있다.
- **승인 권한**: **Moderators 그룹과 superuser만** 댓글 상태를 바꿀 수 있다. Editors는 글 발행 권한이 없는 것과 동일한 이유로 댓글 승인 권한도 없다(`core/migrations`와 동일 패턴으로 `comments/migrations/0002_grant_moderator_permissions.py`가 명시적으로 부여, Editors는 제외).
- **처리 방법**: 목록에서 댓글을 열어 `status` 필드를 "승인 대기" → "승인됨" 또는 "거부됨"으로 바꾸고 저장한다. 함께 표시되는 게시물명/작성자 표시명/본문/마스킹된 접속 IP를 보고 스팸·부적절한 내용 여부를 판단한다.
- **승인 시**: 즉시 해당 게시물 하단 댓글 목록에 노출된다 — 다만 게시물 페이지가 10분 캐시되므로(§2.4와 별개로 공개 뷰 전역 정책), 승인 직후 최대 10분간은 반영이 지연될 수 있다(오류 아님).
- **거부 시**: 공개 화면에 영원히 노출되지 않는다. 완전히 지우고 싶으면 목록에서 삭제(Moderators는 삭제 권한도 있음)할 수 있다 — 삭제하면 복구할 수 없다.
- **자동 알림(2026-09-25 추가)**: 새 댓글이 등록되면 `DJANGO_ADMIN_EMAIL`(500 에러 알림과 동일한 채널)로 즉시 메일이 발송된다 — 게시물 제목/작성자 표시명/본문/모더레이션 화면 링크가 포함된다. `DJANGO_ADMIN_EMAIL`을 설정하지 않았다면 알림이 조용히 발송되지 않을 뿐이며(기동을 막지 않음), 이 경우 위 스니펫 목록을 주기적으로 직접 열어봐야 한다. 메일 발송 자체가 실패해도(SMTP 오류 등) 댓글 저장에는 영향이 없다.
- **수집 정보**: 댓글 작성자에게는 이름(자유입력, 실명 검증 없음)만 받으며 이메일은 받지 않는다 — 회신이 필요한 문의라면 댓글이 아니라 `/cms-admin/settings/core/sitesettings/`에 설정된 연락처 이메일(설정되어 있는 경우)로 별도 안내한다.

## 3. 되돌리기 어려운 작업: 구독자 하드 삭제 (개인정보 파기절차)

**이 서비스에서 가장 신중하게 다뤄야 하는 관리 작업이다. 삭제된 구독자 레코드는 이 화면에서 복구할 방법이 없다.**

### 3.1 이 작업이 왜 위험한가

- `NewsletterSubscriber` 레코드 삭제는 데이터베이스 행을 실제로 지우는 **하드 삭제**다. `status`를 "구독취소"로 바꾸는 것이 아니라 행 자체가 사라진다(`03-system-design.md` §3.2/§5.6에 명시된 v1의 유일한 실제 삭제 경로).
- Django 기본 관리자의 목록 화면에서 체크박스로 여러 건을 선택해 "삭제" 액션을 실행하면 **한 번에 여러 구독자를 동시에 삭제할 수 있다**. 삭제 전 확인 화면이 뜨지만, 검색/필터를 걸어둔 상태에서 "전체 선택"을 잘못 누르면 의도하지 않은 다수 삭제로 이어질 수 있다.
- 삭제된 레코드는 애플리케이션 화면 어디에서도 복구할 수 없다. R2(Cloudflare 오브젝트 스토리지) `backup-private` 버킷에 매일 데이터베이스 백업이 보관되지만, 이 백업에서 복구하는 것은 **DB 전체를 특정 시점으로 되돌리는 인프라 작업**이며, 삭제한 그 구독자 한 명만 선택적으로 되살리는 기능이 아니다. 또한 이 백업은 14일이 지나면 자동으로 만료·삭제된다.

### 3.2 삭제 전 반드시 지킬 확인 절차

1. **삭제 근거를 먼저 확보한다**: 구독자 본인이 탈퇴/삭제를 명시적으로 요청했는지 확인한다(예: 개인정보처리방침에 안내된 연락처로 온 요청). 근거 없이 임의로 삭제하지 않는다.
2. **이메일 검색으로 정확히 그 1건만 특정한다**: 목록 화면에서 검색창에 요청받은 이메일 주소를 정확히 입력해 검색하고, 결과가 요청받은 이메일과 정확히 일치하는지(대소문자·오탈자 포함) 다시 한 번 확인한다. 이메일은 구독 시점에 소문자로 정규화되어 저장되므로, 검색 결과가 없다면 대문자가 섞인 원본 표기로 검색하지 않았는지 확인한다.
3. **체크박스는 확인된 1건만 선택한다.** "전체 선택" 체크박스는 사용하지 않는다. 여러 건을 동시에 처리해야 하는 상황이 실제로 발생하면, 각 건의 요청 근거를 개별적으로 재확인한 뒤 해당 건들만 개별 선택한다.
4. **삭제 실행 전 확인 화면의 이메일 주소를 다시 한 번 육안으로 대조한다.** Django 기본 관리자는 삭제 실행 전 "다음 항목을 삭제하시겠습니까"라는 확인 화면을 보여준다 — 이 화면에 나열된 이메일 주소가 요청받은 이메일과 정확히 일치하는지 확인한 뒤에만 최종 확인을 누른다.
5. **삭제 완료 후 요청자에게 처리 완료를 회신한다**(개인정보처리방침이 명시한 절차 이행 근거를 남기는 차원에서, 회신 이력은 이메일 등 이 시스템 밖에서 보관한다).

### 3.3 확신이 없을 때

- 요청 이메일이 목록에서 여러 건 비슷하게 검색되거나, 요청자 본인 확인이 애매한 경우에는 **삭제를 진행하지 않고** 먼저 요청자에게 재확인하거나 기술 담당자와 상의한다. 잘못 삭제하면 되돌릴 수 없다는 점이 이 판단의 기준이다.
- R2 백업에서 특정 구독자 1건만 복구하는 절차는 이 서비스에 마련되어 있지 않다(위 3.1). "나중에 백업에서 복구하면 된다"고 가정하고 삭제하지 않는다.

## 4. 로그인 실패 시 레이트리밋(429) 동작과 대처 방법

### 4.1 배경 (왜 이 내용이 중요한가)

과거 보안검증(`09-security-audit.md`)에서 최초 점검 시 `/django-admin/login/`(Django 기본 관리자 로그인)에는 무차별대입 방어가 전혀 적용되지 않아 무제한 로그인 시도가 가능한 결함(DEF-09-01, High)이 발견되었다. 이후 재작업을 거쳐 **두 로그인 경로 모두 동일한 레이트리밋으로 보호되도록 수정되었고, 재검증까지 완료되어 최종 판정이 PASS로 갱신**되었다(`09-security-audit.md` 문서 최상단 배너 및 라운드 2 재검증 절 참고). 관리자가 실제로 겪을 수 있는 동작은 아래와 같다.

### 4.2 동작 규칙

- 같은 IP에서 **15분 동안 합산 10회**를 초과하는 로그인 실패(잘못된 비밀번호 등) POST 요청이 발생하면, 11번째 시도부터 즉시 `429`(너무 많은 요청) 응답으로 거부된다.
- **`/cms-admin/login/`(Wagtail)과 `/django-admin/login/`(Django 기본 관리자)은 이 카운터를 서로 공유한다.** 즉 한쪽 화면에서 로그인을 여러 번 틀리면, 다른 쪽 화면에서 시도할 수 있는 남은 횟수도 함께 줄어든다. 예를 들어 `/cms-admin/login/`에서 5회 실패한 뒤 `/django-admin/login/`으로 옮겨 시도해도, 합산 6번째 시도부터는 이미 실패 카운트에 포함되며 합산 11번째 시도에서 429가 발생한다.
  - 이렇게 설계된 이유: 두 로그인 화면이 동일한 계정(같은 `auth_user` 슈퍼유저)을 공유하기 때문에, 만약 카운터가 화면별로 따로 계산된다면 공격자가 시도를 두 화면에 나눠 걸어 실질적인 시도 예산을 2배(IP당 20회)로 늘리는 우회가 가능해진다. 카운터 공유는 이 우회를 막기 위한 의도된 설계다.
- 잠금은 **IP 기준**이며 계정(아이디) 기준 잠금은 아니다. 즉 관리자 본인이 비밀번호를 여러 번 잘못 입력해도 "계정"이 잠기는 것이 아니라, 그 IP에서의 시도가 일시적으로 막히는 것이다(1인 운영 환경에서 계정 자체가 잠기면 대체 관리자가 없어 복구가 어려워지는 상황을 막기 위한 설계).

### 4.3 429가 발생했을 때 대처 방법

1. **15분을 기다린다.** 창 기간(15분)이 지나면 해당 IP의 카운터가 자동으로 초기화되어 다시 시도할 수 있다. 별도의 수동 잠금 해제 절차나 관리 화면은 이 서비스에 없다.
2. 급하게 재시도해야 하는 경우, IP가 바뀌는 다른 네트워크(예: 모바일 데이터 테더링)로 접속을 시도할 수 있다 — 다만 이는 IP만 바뀔 뿐 레이트리밋 자체를 해제하는 공식 절차는 아니며, 정상적인 대응은 15분 대기다.
3. 이 지연은 1인/소규모 운영 규모에서 수용 가능한 트레이드오프로 이미 설계 단계에서 결정된 사항이며(DEC-029), 우회를 위한 화이트리스트/관리자 강제 해제 기능은 v1에 존재하지 않는다.
4. 비밀번호 자체를 잊어버려 반복 실패가 발생하는 경우라면, 429가 풀리기를 기다리는 것과 별개로 비밀번호 재설정이 필요하다 — 재설정 절차(서버 환경변수 조작이 필요한 운영 작업)는 이 문서 범위 밖이므로 `webapp/ADMIN_ACCESS_GUIDE.md`와 운영 인수인계 문서(`docs/harness/11-ops-handoff-runbook.md`)를 참고하거나 기술 담당자에게 요청한다.

## 5. 이상 동작 발견 시 대응

관리자 화면에서 명백히 이상한 동작(예: 권한이 있어야 할 기능이 보이지 않음, 발행한 글이 반영되지 않음, 429가 15분이 지나도 풀리지 않음 등)을 발견하면, 이 문서에 없는 원인 조사나 서버 설정 변경을 관리자가 직접 시도하지 않는다. 이 서비스는 1인/소규모 운영을 전제로 설계되어 있어 관리자 계정 자체가 콘텐츠 전체와 구독자 개인정보를 통제하는 단일 지점이므로, 확신 없는 임의 조치보다 운영 담당자(기술 담당자)에게 확인을 요청하는 것이 안전하다. 장애 대응/에스컬레이션 절차는 `docs/harness/11-ops-handoff-runbook.md`를 따른다.
