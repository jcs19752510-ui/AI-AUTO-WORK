## 1차 검증 (작성자 관점 자가 재검토)

**검토 관점**: 08/09/10단계 산출물과 실제로 일치하는지, 시크릿 값 등 민감정보가 섞여 들어가지 않았는지.

1. **10단계 최종 판정 인용 정확성**: 원본 `10-deploy-test.md` §9는 CONDITIONAL PASS였으나, 문서 최상단 배너 + §9-1 + §11이 DEF-10-01(High)/DEF-10-03(Medium)을 Fixed로 확인하며 판정을 **PASS로 갱신**한다는 것을 정확히 반영했는지 재확인 → Runbook §0-3, §2 전체가 "§9-1/§11 기준"으로 명시적으로 서술되어 있음을 재확인. 원본 §9(CONDITIONAL PASS) 텍스트만 인용하는 실수 없음.
2. **09단계 최종 판정 인용 정확성**: 원본 FAIL(DEF-09-01)과 재작업 라운드2 PASS를 혼동하지 않았는지 재확인 → §7-1이 "재작업 라운드2에서 독립 재현으로 PASS 확정"을 명시하고, §7-3에 잔존 Low 3건(DEF-09-02/03/04)을 정확한 상태(Open/Deferred)로 구분해 기록했음을 확인.
3. **DEF-10-02(환경변수 10개 누락) 반영**: 사용자 지시가 요구한 10개(`DJANGO_ADMIN_EMAIL`, `DJANGO_SUPERUSER_USERNAME/EMAIL/PASSWORD`, `EMAIL_HOST/HOST_USER/HOST_PASSWORD/PORT/USE_TLS`, `SERVER_EMAIL`)가 §3-2 표에 ★표시로 전부 포함되어 있는지 개수 재확인 → `render.yaml` 원문과 대조해 정확히 10개(★) 포함, 나머지 15개(고정값 2 + 필수시크릿 2 + 필수 2 + R2 미디어 4 + R2 백업 3 + 고정값 장애알림 2, 합 15)와 합쳐 25개 전체 커버 확인.
4. **DEF-10-04(롤백 시 보안수정 소실) 반영**: 사용자 지시가 요구한 구체적 식별 기준(`RateLimitedAdminLoginView` 클래스, `config/urls.py`의 오버라이드 경로)이 §2-4/§2-5에 정확히 인용되어 있는지 재확인 → `10-deploy-test.md` DEF-10-04 원문의 식별 기준 문장을 그대로 반영했음을 확인.
5. **DEF-10-05(`.gitattributes` 부재) 반영**: §8 표 #4에 실제 재현 로그(`bash\r: No such file or directory`)와 함께 알려진 제약사항으로 명시했는지 확인 → 반영 완료.
6. **DEC-038(애널리틱스/FAQ 비율 자동집계 미결정) 반영**: §8 표 #5/#6에 "사용자가 직접 결정해야 할 사안"이라는 DEC-038 원문의 판단을 그대로 유지했는지(임의로 "결함"이나 "이미 해결됨"으로 왜곡하지 않았는지) 재확인 → DEC-038 원문 인용과 일치.
7. **실제 벤더 계정 부재 명시**: 사용자 지시가 요구한 "12단계 실배포 시 최초로 실제 벤더 환경을 마주하게 된다"는 점이 §0-1(문서 맨 앞)에 배치되어 있는지 확인 → 배치됨, 운영자가 이 문서를 읽는 첫 순간 이 전제를 인지하도록 구조화.
8. **민감정보 혼입 여부 전수 검토**: 문서 전체에서 `SECRET_KEY=`, `postgres://`, `AKIA`, 실제 이메일/도메인 등 구체적 값 패턴이 있는지 재검색 → §3의 모든 표는 변수명과 "Render 대시보드"/"GitHub Secrets" 같은 관리 위치만 기술하고, §4-2의 `aws s3 ls` 예시도 `<R2_BACKUP_BUCKET_NAME>` 플레이스홀더만 사용함을 재확인. 실제 값 0건.
9. **필수 섹션 커버리지**: 에이전트 정의가 요구하는 8개 섹션(시스템 개요/아키텍처, 배포·롤백 절차 요약, 환경변수·시크릿 이름/관리방법, 모니터링·알림·대시보드·정상범위, 정기 유지보수, 장애대응·에스컬레이션, 09단계 보안 유의사항, 알려진 제약사항) 전부가 문서에 존재하는지 목차 대조 → §1~§8 순서대로 1:1 대응 확인, 누락 없음.

**1차 검증 결과**: 결함 0건. 작성 당시 누락 없이 전 항목 반영 확인.

## 2차 검증 ("처음 온콜을 서는 운영자" 관점 재검토)

**검토 관점**: 이 문서만 받고 그 역할을 처음 맡는 사람이, 추가 질문 없이 온콜을 수행할 수 있는가.

1. **"무엇이 검증됐고 무엇이 안 됐는지" 구분 가능성**: §0-1/§2 전반에 "배포 후 확인 필요"가 반복적으로 명시되어, 온콜 운영자가 이 Runbook의 기준값을 "이미 실측된 사실"로 오인하지 않도록 구조화되어 있는지 재확인 → 충족. 특히 §4-3 KPI 표는 "측정 가능 여부" 컬럼을 별도로 두어 확정치와 잠정치를 시각적으로 분리함.
2. **롤백 실행 순간의 실전성**: 새벽 장애 상황을 가정했을 때, §2-5 체크리스트만 보고 "지금 롤백해도 되는가/롤백 후 뭘 해야 하는가"를 순서대로 실행할 수 있는가 → 4단계 체크리스트가 순서대로(원인 파악 → 보안수정 존재 여부 확인 → destructive 마이그레이션 여부 확인 → 롤백 후 확인 항목) 구성되어 있어 즉시 실행 가능한 수준으로 판단.
3. **환경변수 설정 실전성**: Render 대시보드를 처음 여는 운영자가 §3-2 표 하나만으로 25개 항목을 빠짐없이 채울 수 있는가 → 표가 "구분/변수명/값 성격/관리 방법" 4열로 되어 있어 실행 가능. 다만 실제 값 자체(예: SMTP 벤더 선택, R2 자격증명 발급처)는 이 문서 범위 밖(시크릿 값 원문 기록 금지 원칙)이므로 §3-1에 "실제 값은 벤더 콘솔에서 발급받아야 함"을 명시해 기대치를 정확히 설정했는지 재확인 → 명시됨.
4. **에스컬레이션 공백의 정직성**: 연락처 정보가 비어 있다는 사실이 문서 뒷부분에 조용히 묻혀 있지 않고, 처음 읽는 운영자가 "이 부분은 내가 직접 채워야 한다"는 것을 명확히 인지할 수 있는 위치/문구로 되어 있는지 재확인 → §6-2가 "이는 이 문서가 실수로 누락한 것이 아니라..."로 명시적으로 설명하고, §8 표 #14로도 다시 한번 알려진 제약사항에 등재해 이중으로 노출함. "규칙C: 이상 없음은 근거와 함께" 원칙과 동일하게 "정보 없음도 근거와 함께" 원칙을 적용했음을 확인.
5. **보안 판정 오독 방지**: 09단계가 PASS임에도 "DEF-09-01(High)"이라는 문구가 이력상 등장하는 것을 보고 온콜 운영자가 "아직 위험한 상태"라고 오해하지 않도록 §7-1에서 최종 판정을 먼저 명확히 선언한 뒤 §7-2/§7-3에서 세부를 다루는 순서로 배치되어 있는지 재확인 → 순서 적절, 오독 가능성 낮다고 판단.
6. **다른 3개 문서와의 정보 경계**: 이 Runbook에 사용자 매뉴얼/관리자 매뉴얼/API 문서 영역의 내용(예: 화면 사용법, API 엔드포인트 스펙)이 섞여 들어가지 않았는지 재확인 → 섞이지 않음. §1에서 "정식 API 없음, `11-api-reference.md`(해당 없음 문서) 참고 안내"로 경계를 명확히 하되 API 스펙 자체는 기술하지 않음.

**2차 검증 결과**: 결함 0건. 정보 공백(에스컬레이션 연락처 등)은 은폐하지 않고 명시적으로 노출했음을 재확인.
