## 0. 프로젝트 자체 스캔 결과 (기획 전제)

기획 착수 전 `AI-AUTO-WORK` 프로젝트 루트를 `Read`/`Glob`/`Bash`로 스캔한 결과:

- `git` 저장소가 초기화되어 있지 않음(`git log` 실행 시 "not a git repository") → 커밋 이력, 기존 이슈/백로그 없음. MCP 이슈 트래커도 미연동(DEC-001)이므로 "기존에 계획된 기능 목록"을 참조할 소스가 전혀 없다.
- 프로젝트 루트에는 하네스 자체 파일(`ORCHESTRATOR.md`, `.claude/agents/`, `templates/`, `automation/`, `docs/harness/`)만 존재하고, 대상 서비스(블로그 사이트)의 소스 코드/디자인 산출물은 전혀 없음 → DEC-003("기존 자산 없음")과 일치. 따라서 "기존 시스템과의 호환성" 제약은 발생하지 않으며, 전부 그린필드(green-field) 신규 개발이다.
- `추가개선사항정리.md`에는 "20년차 개발/기획/설계/보안/디자인 기준을 반드시 지키고, 모르면 물어보고, 2번 작업 요청시키지 말고, 내부테스트 결과서 완벽하게 작성하라"는 프로젝트 운영자의 메모가 있음 → ORCHESTRATOR.md 규칙 A/B/C와 동일한 취지이며 이미 반영 중이므로 기획 내용에 별도 영향 없음(참고 확인 완료).
- `GIT정보.MD`는 git 초기 설정 커맨드 모음(브랜치 `PROD_SCH`, 리모트 `final-project`)으로, 배포 대상 리포지토리 관례를 보여주나 서비스 기능과는 무관.

**결론**: 이 기획서는 순수하게 01번 산출물 + 하네스 규칙만을 근거로 작성되며, 참조할 기존 기능/백로그가 없다는 것 자체가 스캔의 확정적 결과다.

## 1. 서비스/기능 개요 및 목적

워드프레스(MySQL 전제) 대신 **Python + PostgreSQL(Neon) + Render** 스택으로 신규 구축하는 **블로그/콘텐츠 사이트**다(DEC-002, DEC-004). 목적은 다음 두 가지다.

1. **데이터/인프라 완전 소유권을 가진 콘텐츠 발행 플랫폼 제공**: Medium/Substack 같은 호스티드 플랫폼("임대한 땅", 01 §3-2)에 종속되지 않고, 운영자가 콘텐츠·독자 데이터를 전적으로 소유한다.
2. **AI 검색 시대에도 지속 가능한 독자 도달 채널 확보**: 유기 검색 트래픽이 구조적으로 감소하는 환경(01 §2-3)에서, 검색 엔진 의존도를 낮추고 RSS/이메일 구독 같은 직접 채널을 함께 갖춘 콘텐츠 사이트를 만든다.

프레임워크(Wagtail vs Django-CMS 등) 최종 선택은 3단계 설계자의 권한이며(DEC-004, 01 §3-1), 이 기획서는 어느 쪽을 선택하든 적용 가능하도록 "Python/Django 생태계 기반 CMS"라는 표현으로 기능을 정의한다.

## 2. 타깃 사용자 및 페르소나

> **[가정 A1]** 01번 조사는 사용자 요청에 따라 타깃을 의도적으로 미확정 상태로 남겼다(01 §1, §4, §7-1, §8-1). 이 기획서는 "이 두 입력만으로 끝까지 완성"해야 하므로, 아래 근거에 기반해 타깃을 자체 판단으로 구체화한다. 이는 콘텐츠 주제(니치) 자체를 확정하는 것이 아니라 **운영 규모와 이용 행태** 수준의 합리적 범위 설정이며, 근거는 다음과 같다.
> - 01 §3-2: 자체 구축 사이트는 "설치 즉시 사용 가능한 생태계가 없다"는 것이 구조적 약점이며 "유지보수 부담이 전적으로 운영자 책임"이다 → 대규모 편집팀·복잡한 권한체계를 요구하는 매체보다, 관리 가능한 소규모 운영에 적합하다.
> - 01 §6: Render/Neon 무료 티어(콜드스타트, 월 750시간, 0.5GB 저장)로 시작하는 구조 → 대형 매체가 아니라 소규모로 시작해 성장하는 프로젝트에 부합.
> - 01 §2-2, §4: 크리에이터 이코노미(Substack/Ghost) 트렌드, "1인 창작자가 무료 콘텐츠로 발견 → 이메일 전환 → 수익화"라는 2026년 주류 모델.
>
> 따라서 아래 페르소나로 확정하고 3단계 이후 검증 대상으로 남긴다.

### 페르소나 1 — 운영자(콘텐츠 오퍼레이터)
- 1인 또는 소규모(2~3인) 팀. 특정 주제에 대한 전문성을 가지고 정기적으로 글을 발행한다.
- 워드프레스 플러그인 생태계 없이도 필요한 기능(SEO, 이미지 업로드, 구독 폼 등)을 직접 갖춘 최소 기능 제품(MVP)을 원한다.
- 검색 유입 감소를 인지하고 있으며, 이메일 구독자 같은 직접 채널 확보에 관심이 있다(01 §4).

### 페르소나 2 — 독자
- 특정 주제에 관심이 있어 재방문하거나 구독하는 독자. 검색엔진의 AI 요약(제로클릭)으로 정보를 먼저 소비한 뒤, 더 깊은 내용이 필요할 때만 원문 사이트를 방문하는 경향이 있다(01 §2-3).
- 모바일/데스크톱 어느 환경에서도 콘텐츠를 읽을 수 있어야 한다(반응형 요구).

### 콘텐츠 주제 범위에 대한 명시적 정책 (가정 A2)
콘텐츠의 구체적 니치(기술/라이프스타일/취미 등)는 여전히 미확정이며, 이는 **콘텐츠 운영 정책의 문제이지 시스템 기능 요구사항이 아니므로** 시스템 설계에 영향을 주지 않는다. 다만 01 §5 부록에서 "규칙 I(규제 민감 도메인)은 현재 해당 없음이나, 콘텐츠 주제가 금융/의료/법률/보험 조언성으로 좁혀지면 재검토가 필요하다"고 명시했으므로, 이 기획서는 **금융/의료/법률/보험 등 인허가 규제 대상이 될 수 있는 "조언·추천"형 콘텐츠는 서비스 정책상 게시하지 않는다**는 제약을 채택해 규칙 I 비해당 상태를 유지한다(REQ-015, §4 참고). 이 정책이 향후 변경되면 반드시 규칙 F(피드백 루프)에 따라 1단계(규칙 I 재조사)부터 재작업해야 한다.

## 5. 성공 지표 (KPI)

> 업계 표준 벤치마크가 01번 조사 범위에 없었으므로, 아래 수치는 모두 **[가정]** 표시된 초기 목표치이며, 실측 데이터 확보 후(운영 3개월 시점) 재조정을 권고한다. 측정 불가능한 "많이/빠르게" 식의 목표는 사용하지 않았다.

1. **트래픽**: 출시 후 3개월 시점 월간 순방문자(UV) 500명 이상 [가정 — 초기 목표치].
2. **구독 전환(REQ-016)**: 방문자 대비 이메일 뉴스레터 구독 신청 전환율 1% 이상 [가정].
3. **가용성**: 무료 티어 운영 구간에는 Render 월 750 인스턴스시간 한도 초과로 인한 서비스 중단 0회. 유료 전환 이후에는 업타임 99.5% 이상.
4. **응답 성능**: 콜드스타트가 발생하지 않은 요청 기준 TTFB(Time To First Byte) 1.5초 이내. 콜드스타트 발생 케이스(REQ-011)는 별도 카운트해 비율로 관리(목표: 전체 요청의 5% 미만).
5. **SEO/콘텐츠 품질**: 신규 발행 포스트 중 질문-답변형 구조(REQ-017 가이드라인) 적용 비율 80% 이상.
6. **법적 준수**: 개인정보처리방침(REQ-007)·쿠키 고지(REQ-008)·이용약관(REQ-009) 페이지가 배포 전 100% 게시·최신화되어 있어야 하며, 10단계(배포테스트) 체크리스트 항목으로 등록한다.
7. **데이터 안전성**: Neon PITR 6시간 한계를 보완하는 별도 백업(REQ-013)이 정의된 주기대로 100% 수행되었는지 로그로 확인 가능해야 한다.

## 6. 제약 조건

### 기술 제약 (확정, DEC-004 기반)
- 언어/런타임: Python (확정, 변경 불가)
- DB: PostgreSQL(Neon) (확정)
- 배포: Render (확정)
- CMS/프레임워크: Python/Django 생태계 내에서 3단계가 최종 선택(Wagtail 또는 Django-CMS 등, 01 §3-1). Node 기반(Directus/Strapi/Payload)은 언어 제약과 배치되어 제외.
- 미디어 파일은 Render 컨테이너 로컬 파일시스템에 영속 저장 불가 → S3 호환 오브젝트 스토리지 필수 연동(REQ-006).

### 인프라 한계 제약 (01 §6)
- Render 무료 티어: 15분 유휴 시 스핀다운, 재기동 약 1분(Django 앱은 30초+ 가능), 월 750 인스턴스시간 한도.
- Neon 무료 티어: 저장 0.5GB, 월 100 컴퓨트시간, 최대 2 CU, scale-to-zero, 프로젝트 1개 한도, PITR 보존 6시간.
- 위 수치는 3rd-party 리뷰 출처 기반으로, 공식 pricing/docs 페이지로 재확인이 권고된다(01 §7-6). 위 한계는 "리스크"가 아니라 **제약 조건**으로 다루며, REQ-011·012·013으로 명시적 대응/수용 방안을 등록했다.

### 기존 시스템 호환성 제약
- §0 스캔 결과: 기존 소스 코드/디자인 자산 없음(DEC-003과 일치) → 호환성 제약 없음. 전부 그린필드 개발.

### 일정/예산 제약
- 01번 산출물과 프로젝트 문서 어디에도 구체적 일정(출시일)이나 예산 정보가 없다. **[가정 A6]** 별도 마일스톤 날짜를 임의로 만들지 않고, §9 작업 단위(Work Unit)의 우선순위·의존관계 기반 순차 진행을 전제로 한다. 실제 일정/예산이 확정되면 규칙 F에 따라 이 섹션을 갱신해야 한다.

**[2단계] 수익화 모델을 무엇으로 할 것인가(완전 무료 / 광고 기반 / 유료 구독) / 01번 조사(§5)가 사용자의 광고·수익화 계획을 확인하지 못한 채 "확인 필요"로 남겼고, 이는 ORCHESTRATOR.md 규칙 A-③이 예로 든 비가역적 결정("유료/무료 모델")에 정확히 해당해 임의 추정이 금지되기 때문 / 선택지와 트레이드오프는 아래 참고**

- 왜 판단이 안 되는가(상세): 선택지에 따라 데이터 모델(구독/결제 스키마), 3rd-party SDK 통합(결제 게이트웨이, 광고 SDK), 보안 범위(결제 정보 처리 시 PCI 고려), 개인정보/쿠키 고지 범위(광고 SDK 도입 시 위탁처리 조항 추가)가 모두 달라진다.
- 선택지와 트레이드오프:
  - (a) **완전 무료/비영리**: 구현이 가장 단순하고 법적 부담이 최소. 대신 장기 운영비(유료 티어 전환 비용)를 운영자가 전액 부담.
  - (b) **광고 기반(애드센스 등)**: 초기 구현 부담은 상대적으로 낮으나(SDK 연동 수준), 쿠키/개인정보 고지 범위 확대(REQ-008 확장) 필요, 광고 노출이 콘텐츠 신뢰도/UX에 영향을 줄 수 있음.
  - (c) **유료 구독/멤버십**: 크리에이터 이코노미 트렌드(01 §2-2)에 부합하나, 결제 게이트웨이 연동, 구독자 DB, 환불/해지 정책, 보안 검증(9단계) 범위가 크게 늘어나는 비가역적 아키텍처 결정.
- 이 질문에 대한 답이 오면 `docs/harness/decisions.md`에 규칙 G에 따라 기록하고, 이 문서(§4, §7, §9)를 규칙 F에 따라 갱신한다.
