## 0. 개요 및 설계 전제

이 문서는 **방문자(독자)용 프런트엔드 화면**과 **운영자의 최소 콘텐츠 발행 워크플로**를 다룬다. Wagtail 어드민 UI 자체(로그인 화면, 페이지 편집기, 스트림필드 블록 에디터 등)는 **벤더가 기본 제공하는 화면이며 이번 디자인서가 새로 설계하지 않는다** — 03 §2.1(DEC-006)에서 Wagtail을 채택한 핵심 근거 자체가 "편집 워크플로를 프레임워크 표준 기능으로 그대로 쓴다"는 것이었으므로(DEC-007), 이를 커스텀 UI로 다시 그리는 것은 과설계다. 대신 §1.2/§2(OP 항목)에서 **운영자가 Wagtail 기본 어드민의 어떤 기능을 어떤 순서로 써서 REQ-001을 달성하는지**를 워크플로 수준으로 서술한다.

핵심 제약(상위 문서에서 계승, 임의 변경 없음):
- 회원가입/로그인 UI 없음(DEC-009) — 구독자는 이메일만 남기는 무인증 폼(REQ-016)으로 대체.
- 수익화 UI(광고 배너/결제) 없음(DEC-005, REQ-022~024 Out-of-Scope).
- SPA/클라이언트 프레임워크 없음(03 §4) — 서버사이드 렌더링(Django 템플릿) 기반, 모든 화면은 JS 없이도 동작해야 한다(점진적 향상만 허용).
- 검색(REQ-018)·댓글(REQ-019)·소셜 공유 버튼(REQ-020)은 v1 Could 항목으로 **화면에 포함하지 않는다**(03 §1.2 "자리만 마련"과 일치 — 지금 UI에 노출하지 않고, 아키텍처만 확장 가능하게 열어둠). 사용하지 않는 기능을 내비게이션에 노출하는 것은 "있는데 못 쓰는 UI"보다 나쁜 "없는데 있어 보이는 UI"이므로 원천 배제한다.

## 1. 핵심 사용자 플로우

### 1.1 방문자(독자) 플로우 — 텍스트 와이어플로우

```
[검색엔진/AI 요약/소셜 링크]
  └─▶ S-02 게시물 상세  (방문자는 S-01 홈을 거치지 않고 바로 진입하는 경우가 다수 — 01번 §2-3 "AI 요약 우선 소비" 행태 반영)
        ├─▶ [카테고리 배지 클릭] ─▶ S-03 카테고리 목록
        ├─▶ [태그 칩 클릭]       ─▶ S-04 태그 목록
        ├─▶ [본문 스크롤/하단]   ─▶ 뉴스레터 구독 폼(컴포넌트, 인라인) 제출 ─▶ 성공/에러 인라인 메시지 (페이지 이동 없음)
        ├─▶ [RSS 아이콘]         ─▶ 새 탭 `/feed.xml` (브라우저/피드리더가 처리, 사이트 내부 화면 아님)
        ├─▶ [헤더 로고]          ─▶ S-01 홈
        └─▶ [푸터 법적 링크]     ─▶ S-05 개인정보처리방침 / S-06 이용약관 / S-07 쿠키 고지

[직접 방문/북마크]
  └─▶ S-01 홈 (발행글 목록, 페이지네이션)
        ├─▶ [게시물 카드 클릭]      ─▶ S-02 게시물 상세
        ├─▶ [카테고리 필터]         ─▶ S-03 카테고리 목록
        ├─▶ [태그 필터]             ─▶ S-04 태그 목록
        ├─▶ [다음 페이지 버튼]      ─▶ S-01 홈 (`?page=n`)
        └─▶ [최초 방문 쿠키 배너]   ─▶ "확인" 클릭 시 닫힘(로컬 저장, 재방문 시 미노출) / "자세히 보기" ─▶ S-07

[콜드스타트 상황 — 유휴 15분↑ 이후 첫 요청, DEC-011/03 §6.3]
  └─▶ Render 플랫폼 자체 스핀업 로딩 화면 노출 (우리 앱 밖, 커스터마이즈 불가 — §2 "참고: 우리가 설계하지 않는 화면" 참고)
        └─▶ (최대 30초+ 후) 앱 기동 완료 ─▶ 원래 요청한 화면(S-01~S-09 중 하나) 정상 렌더 ─▶ 첫 페이지뷰 이후에는 §5/§6 성능 원칙에 따라 빠르게 응답

[존재하지 않는 경로 / 미공개·예약전·만료된 게시물]
  └─▶ S-08 404 Not Found

[서버 오류 / Gunicorn 워커 타임아웃 등]
  └─▶ S-09 500 서버 오류 (Django가 처리 가능한 경우) — 플랫폼 레벨 타임아웃(502 등)은 앱이 렌더링을 제어할 수 없는 영역이며 §7에 리스크로 명시
```

### 1.2 운영자 워크플로 (Wagtail 기본 어드민 그대로 사용, 화면 재설계 아님)

```
운영자 로그인(Wagtail 기본 로그인 화면, 세션 인증 — DEC-009)
  └─▶ OP-01 페이지 트리에서 "블로그 인덱스" 하위에 신규 게시물 위치 확인
        └─▶ OP-02 제목/본문(StreamField: 문단/이미지/인용/FAQ)/카테고리/태그/대표이미지 작성 → "임시저장"
              └─▶ OP-03 미리보기(Wagtail 기본 Preview) — live=False 상태이므로 방문자에게는 보이지 않음(S-08과 동일 취급)
                    └─▶ OP-04 예약발행 설정: `go_live_at`(공개 시작)/`expire_at`(공개 종료) 입력 또는 즉시 게시
                          └─▶ 게시(live=True) ─▶ 프런트엔드 S-01/S-02/S-03/S-04/RSS/사이트맵에 자동 반영(03 §4 라우팅 규칙)
                                └─▶ OP-05 이후 수정 시 리비전 이력에서 이전 버전과 비교/복원 가능(Wagtail 기본 기능)
운영자(수시)
  └─▶ OP-06 Category Snippet CRUD(카테고리 신설/수정 — REQ-002, REQ-015 화이트리스트 운영정책 실행 지점)
  └─▶ OP-07 뉴스레터 구독자 탈퇴 요청 접수 시 Django/Wagtail 어드민에서 해당 NewsletterSubscriber 레코드 수동 하드 삭제(03 §5.6 파기절차)
```

**설계 판단(근거 명시, 되돌리기 쉬움)**: 위 OP 화면들은 Wagtail이 제공하는 기본 UI를 그대로 쓰므로 이 문서는 그 UI의 레이아웃/컴포넌트를 다시 그리지 않는다. 대신 "어떤 상태(초안/예약/게시/만료)가 프런트엔드의 어떤 노출 결과로 이어지는가"만 명확히 규정해, 운영자가 헷갈리지 않게 한다(아래 표).

| Wagtail 상태 | 프런트엔드 노출 | 근거 |
|---|---|---|
| 임시저장(초안, `live=False`) | 비노출. `/blog/<slug>/` 직접 접근 시 404 | 03 §4 GET `/blog/<slug>/` 응답 규칙 |
| 예약발행 대기(`go_live_at`이 미래) | 비노출(404) | 상동 |
| 게시됨(`live=True`, `go_live_at` 도달) | S-01/S-03/S-04 목록에 노출, S-02 상세 정상 접근 | 상동 |
| 만료(`expire_at` 경과) | 비노출(404) — Wagtail 표준 동작 | 상동 |

## 2. 화면별 명세

각 화면은 **목적 → 관련 REQ/라우트(03 §4) → 구성요소 → 상태(기본/빈/로딩/에러)** 순으로 기술한다. "로딩" 상태는 이 서비스가 서버사이드 렌더링(SPA 아님, 03 §4)이므로 원칙적으로 **브라우저 네이티브 내비게이션 로딩**(주소창 진행 표시줄)이며, 클라이언트 XHR 기반 로딩 스피너는 뉴스레터 폼 등 명시적으로 점진적 향상을 적용한 컴포넌트에만 해당한다는 점을 화면마다 명시한다.

### S-01 홈 (블로그 목록)
- **목적**: 발행된 게시물을 최신순으로 노출해 재방문/탐색 진입점 제공.
- **라우트/REQ**: `GET /`(03 §4), REQ-003, REQ-014.
- **구성요소**: Header, PostCard(반복), Pagination, Footer, CookieConsentBanner(최초 방문 시).
- **상태**
  - 기본: PostCard 그리드/리스트 + Pagination.
  - 빈 상태(게시물 0건, 런칭 초기): "아직 게시된 글이 없습니다. 곧 첫 글로 찾아올게요." 문구 + 뉴스레터 구독 폼 강조 배치(빈 상태를 구독 전환 기회로 전환).
  - 로딩: 브라우저 네이티브 내비게이션 로딩(별도 스켈레톤 없음, SSR 특성상 전체 HTML이 한 번에 도착).
  - 에러: 500(S-09로 위임).

### S-02 게시물 상세
- **목적**: 단일 게시물 전문 열람, AI 검색 대응 구조화 데이터 제공(REQ-017).
- **라우트/REQ**: `GET /blog/<slug>/`(03 §4), REQ-003, REQ-005, REQ-014, REQ-017.
- **구성요소**: Header, Breadcrumb(홈 > 카테고리 > 제목), CategoryBadge, TagChip(복수), ArticleBody(StreamField 렌더러 — 문단/이미지/인용/FAQ 블록), 작성자 바이라인(owner 표시명, 03 §4 JSON-LD 매핑과 동일 소스), 게시일/수정일(`first_published_at`/`last_published_at`), NewsletterSubscribeForm(본문 하단 인라인), JSON-LD `BlogPosting`(비가시 `<script type="application/ld+json">`), RSSIconLink, Footer.
- **상태**
  - 기본: 위 구성요소 전부 렌더.
  - 빈 상태: 해당 없음(단건 조회이므로 "없음" 대신 404로 처리).
  - 로딩: 브라우저 네이티브 로딩. 대표이미지는 `loading="lazy"` + 명시적 width/height로 레이아웃 시프트 방지(§5).
  - 에러: 미공개/예약전/만료/존재하지 않는 slug → **404(S-08)**. `live=True`이지만 대표이미지가 R2에서 일시적으로 로드 실패하는 경우 → 이미지 자리에 대체 텍스트(alt)만 노출되는 "이미지 깨짐" 상태를 허용(이미지 실패가 게시물 전체를 500으로 만들지 않도록 템플릿 레벨에서 격리).

### S-03 카테고리 목록
- **목적**: 특정 카테고리에 속한 게시물만 모아보기.
- **라우트/REQ**: `GET /category/<slug>/`(03 §4), REQ-002, REQ-003.
- **구성요소**: Header, Breadcrumb, PostCard(반복), Pagination, Footer.
- **상태**
  - 기본: PostCard 리스트.
  - 빈 상태: **카테고리 자체는 존재하나(Category Snippet, 03 §3.2) 소속 게시물이 아직 0건**인 경우 — "이 카테고리에는 아직 게시된 글이 없습니다." + 홈으로 이동 CTA. (카테고리 slug 자체가 존재하지 않으면 빈 상태가 아니라 **404**로 처리 — 03 §4 표에 명시된 "404(존재하지 않는 카테고리)"와 일치)
  - 로딩: 네이티브.
  - 에러: 404(존재하지 않는 카테고리, 03 §4).

### S-04 태그 목록
- **목적**: 특정 태그가 달린 게시물 모아보기.
- **라우트/REQ**: `GET /tag/<slug>/`(03 §4), REQ-002, REQ-003.
- **구성요소**: S-03과 동일 패턴.
- **상태**
  - 기본/빈 상태/로딩: S-03과 동일 원칙 적용 — django-taggit Tag 레코드가 존재하지만(과거 태깅 이력) 현재 `live` 게시물이 0건이면 빈 상태, Tag 레코드 자체가 없으면 404.
  - 에러: 404(03 §4 "GET /tag/<slug>/ ... 404").

### S-05 개인정보처리방침
- **목적**: REQ-007 법적 고지. 수집 항목(이메일뿐), 보관기간, 파기절차, **제3자 위탁(Render/Neon/Cloudflare R2/GitHub Actions) 및 국외이전 여부**(03 §5.6) 명시.
- **라우트/REQ**: `GET /privacy-policy/`(03 §4), REQ-007.
- **구성요소**: Header, Breadcrumb, 리치텍스트 본문, "최종 업데이트: {last_published_at}" 메타(Wagtail Page 표준 필드, 03 §3.2), Footer.
- **상태**: 빈 상태 없음(콘텐츠 필수 게시, KPI §5 항목 6). 로딩: 네이티브. 에러: 500(S-09).
- **참고(법률 자문 필요)**: 03 §5.6이 명시한 대로 이 문서의 실제 문구는 법률 검토가 필요하며, 이 디자인서는 "어떤 정보가 화면에 있어야 하는가"만 규정하고 문구 자체를 대신 작성하지 않는다.

### S-06 이용약관 (콘텐츠 정책 섹션 포함)
- **목적**: 저작권/이용자 콘텐츠 권리(REQ-009) + **콘텐츠 정책(REQ-015, 규칙 I 대응)** 게시.
- **라우트/REQ**: `GET /terms/`(03 §4), REQ-009, REQ-015.
- **구성요소**: Header, Breadcrumb, 목차(TOC) 앵커 링크, 리치텍스트 본문(이용약관 섹션 + "콘텐츠 정책" 하위 섹션), "최종 업데이트" 메타, Footer.
- **디자인 판단(근거 명시)**: 03 §5.6은 REQ-015 콘텐츠 정책을 "legal 앱의 콘텐츠 정책 페이지에 게시"라고 서술했지만, 03 §3.2의 `LegalPage` 모델은 개인정보처리방침/이용약관/쿠키고지 **3종**으로만 명시되어 있고 03 §4 라우트 표에도 콘텐츠 정책 전용 URL이 없다. 새 라우트를 임의로 발명하는 대신(설계서에 없는 API를 있다고 가정 금지), **기존 3개 라우트 중 성격이 가장 가까운 `/terms/`(이용약관) 페이지 안에 "콘텐츠 정책" 하위 섹션으로 통합**한다. 이는 (a) 새로운 URL/뷰/데이터 요구가 전혀 생기지 않고, (b) 이미 `LegalPage`가 리치텍스트 기반이라 섹션 추가에 스키마 변경이 불필요하며, (c) 되돌리기 쉬운(리치텍스트 내용 편집만으로 가역) 결정이기 때문이다. 별도 페이지가 꼭 필요하다고 판단되면 5단계 착수 전 규칙 F로 03 §3.2/§4에 `LegalPage` 4번째 서브타입과 라우트를 추가하는 재작업을 권고한다(§7에 이슈로 재기록).
- **상태**: 빈 상태 없음. 로딩: 네이티브. 에러: 500(S-09).

### S-07 쿠키 사용 고지
- **목적**: REQ-008 쿠키 고지. 세션/CSRF 등 필수 쿠키와, `SiteSettings.analytics_id_optional`(03 §3.1)이 향후 설정될 경우의 애널리틱스 쿠키 가능성을 조건부로 설명.
- **라우트/REQ**: `GET /cookies/`(03 §4), REQ-008.
- **구성요소**: Header, Breadcrumb, 리치텍스트 본문(쿠키 목적/보관기간 표), Footer.
- **상태**: 빈 상태 없음. 로딩: 네이티브. 에러: 500(S-09).

### S-08 404 Not Found
- **목적**: 미공개/예약전/만료/존재하지 않는 리소스에 대한 일관된 안내(미공개 게시물 존재 여부를 추측하게 하지 않음 — 보안·UX 원칙 동시 충족).
- **라우트/REQ**: 03 §4의 모든 404 케이스(게시물/카테고리/태그).
- **구성요소**: Header, 에러 일러스트/아이콘(장식용, `aria-hidden`), "페이지를 찾을 수 없습니다" 메시지, 홈으로 이동 CTA, 검색 유도 문구는 **넣지 않음**(REQ-018 내부 검색 v1 미구현이므로 없는 기능으로 유도 금지).
- **상태**: 이 화면 자체가 "에러 상태" 화면. 별도 하위 상태 없음.

### S-09 500 서버 오류
- **목적**: 예기치 못한 서버 오류 시 브랜드 톤 유지 + 복구 경로 제공. Django가 처리 가능한 애플리케이션 레벨 500에 한해 커스텀 템플릿 적용.
- **구성요소**: Header(내비 없이 로고만, 오류 상황에서 추가 클릭 유도 최소화), "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요." 메시지, 새로고침/홈으로 CTA.
- **한계(명시적 트레이드오프)**: Gunicorn 워커 타임아웃(03 §6.4, 약 30초) 등 **플랫폼/서버 레벨에서 요청이 강제 종료되는 경우 이 커스텀 화면이 아니라 Render/브라우저의 일반 오류 화면이 표시될 수 있다** — 이는 Django 코드가 개입하기 전에 발생하므로 우리 화면 설계로 제어할 수 없는 영역이다. §7에 리스크로 재기록.

### 전역 컴포넌트 (모든 화면 공통, 화면 아님)
- **Header/Nav**: 로고(홈 링크), 카테고리 목록(전체 노출 또는 "더보기" — 카테고리 수가 5~6개를 넘으면 드롭다운, 03 §3.2 Category Snippet은 운영자가 자유롭게 추가 가능하므로 개수 상한을 가정하지 않고 반응형으로 처리), RSSIconLink. 검색/로그인 버튼 **없음**(REQ-018 미구현, DEC-009 무인증).
- **Footer**: 법적 링크 3종(S-05/06/07), 저작권 표기, RSS 링크, **콜드스타트 투명성 안내 문구**(아래 "콜드스타트 UX 설계" 참고), 뉴스레터 구독 폼(선택적 배치 — 홈/목록형 화면 한정, 상세 화면은 본문 하단 인라인과 중복 배치하지 않음).
- **CookieConsentBanner**: 최초 방문 시 화면 하단 고정 배너, "확인" 클릭 시 `localStorage`에 플래그 저장 후 재방문 시 미노출. GDPR식 거부/세부설정 옵션은 **넣지 않음**(REQ-021 Out-of-Scope, DEC-005/02 가정 A3와 일관).
- **NewsletterSubscribeForm**: §4 컴포넌트 명세 참고.

### 콜드스타트 UX 설계 (REQ-011, DEC-011, 03 §6.3 연계 — 명시적 설계 판단)
03 §1.2 모듈 경계 표는 `core` 앱 책임으로 "콜드스타트 안내 뷰"를 언급하지만, 동시에 03 §2.4는 "재기동 중 Render가 자체적으로 로딩 페이지를 자동 표시"하며 이는 **우리 Django 앱이 아직 기동되지 않은 시점에 플랫폼이 가로채 보여주는 화면**이라고 명시한다. 즉 앱 코드가 실행되기 전이므로, 우리 앱이 "실시간 콜드스타트 로딩 화면"을 만드는 것은 **아키텍처적으로 불가능**하다(요청이 우리 코드에 도달한 시점엔 이미 앱이 깨어난 뒤다). 이를 프런트엔드 개발자가 헛수고하지 않도록 명확히 하기 위해 다음과 같이 역할을 분리한다(근거를 남긴 자체 판단, 되돌리기 쉬움 — 카피/배치 수정만으로 조정 가능하므로 decisions.md에 별도 등재하지 않음).

1. **1차 방어선(플랫폼)**: Render 자체 스핀업 로딩 화면. 우리가 디자인하지 않으며 디자인할 수도 없다.
2. **2차 방어선(우리 앱, 기대치 설정)**: 별도 라우트/DB 필드를 새로 만들지 않고, **전역 Footer에 고정 안내 문구**(정적 템플릿 카피, 예: "⚡ 무료 인프라로 운영 중이라 오랜만에 방문하시면 첫 로딩이 최대 30초 이상 걸릴 수 있어요")를 상시 노출한다. `<details>/<summary>` 같은 순수 HTML 아코디언으로 1~2문장 추가 설명을 넣을 수 있으며, 이는 새 페이지/새 데이터 없이 구현 가능하다. 운영자가 이 문구를 어드민에서 직접 수정하고 싶다면 `SiteSettings`에 필드를 추가하는 것은 향후 규칙 F 재작업 대상으로 남긴다(현재 03 §3.1 `SiteSettings`에는 해당 필드가 없으므로 v1은 템플릿 하드코딩 카피로 처리).
3. **3차 방어선(체감 성능, 콜드스타트 종료 이후)**: 앱이 깨어난 뒤 첫 페이지 렌더가 최대한 가볍도록 — 렌더 블로킹 JS 없음(§0), 이미지 `loading="lazy"` + 명시적 크기(§5), 뷰 캐시(03 §2.5)로 두 번째 방문자부터는 훨씬 빠르게 응답. 이는 "로딩 화면 디자인"이 아니라 "로딩 자체를 줄이는" 접근이며, 03 §6.4의 Neon 콜드스타트(수백 ms)도 같은 원리로 흡수된다.

## 5. 접근성 기준 (최소 WCAG 2.1 AA)

- **색상 대비**: 본문 텍스트 4.5:1 이상, 큰 텍스트(18pt+ 또는 14pt+bold)·UI 컴포넌트 경계 3:1 이상 — §3.1 토큰이 모두 이 기준을 상회하도록 사전 검증됨. 정보를 색상만으로 전달하지 않는다(예: 카테고리 배지는 색+텍스트 병행, 폼 에러는 색+아이콘+텍스트 병행).
- **키보드 내비게이션**: 모든 인터랙티브 요소(링크/버튼/폼 필드/쿠키 배너 버튼)는 Tab 순서로 접근 가능해야 하며, 포커스 트랩(모달처럼 키보드를 가두는 요소)은 v1에 없음(쿠키 배너는 비모달, 콘텐츠 위를 덮지 않고 닫기 전에도 뒤 콘텐츠 탐색 가능). Escape 키로 배너를 닫을 수 있게 한다(있으면 좋음, 없어도 "확인" 버튼으로 대체 가능하므로 Should).
- **스킵 링크**: 모든 화면 최상단에 "본문으로 바로가기" 링크(평소 숨김, 키보드 포커스 시 노출) 배치.
- **시맨틱 구조**: `header`/`nav`/`main`/`footer` 랜드마크 사용, 헤딩 레벨은 건너뛰지 않고 순차 사용(H1은 화면당 1개 — 게시물 상세는 게시물 제목이 H1).
- **폼 접근성**: 모든 입력에 `<label>` 명시 연결(placeholder만으로 라벨 대체 금지), 에러 메시지는 `aria-describedby`로 해당 필드와 연결하고 텍스트로 명시(색상만 X). 허니팟 필드는 `aria-hidden="true"` + `tabindex="-1"`로 스크린리더/키보드 사용자 경험을 방해하지 않으면서 봇만 속인다(03 §5.3 요건과 접근성 요건의 교차 지점).
- **이미지 대체텍스트**: 모든 비장식 이미지는 alt 필수. 대표이미지(`featured_image`)는 Wagtail `Image.title`을 기본 alt로 사용(Wagtail 표준 동작)하되, **§7에서 식별한 대로 StreamField 이미지 블록에는 전용 alt 입력 필드가 03 설계서에 명시되어 있지 않으므로, 5단계(WU-02) 구현 시 이미지 블록에 alt 텍스트 필드를 반드시 포함해야 한다**(접근성 요건으로 인한 구현 요구사항 — 새 데이터 요구가 아니라 이미 "이미지 블록"에 포함되어야 할 표준 하위 필드).
- **터치 타겟**: 최소 24×24px(WCAG 2.2 AA), 모바일 주요 액션(구독 버튼, 페이지네이션)은 44×44px 권장.
- **모션**: 자동재생 애니메이션 없음. 쿠키 배너 등장 애니메이션은 `prefers-reduced-motion: reduce` 시 비활성화.
- **언어**: `<html lang="ko">`. 콘텐츠 사이트이므로 향후 다국어(REQ-021 Out-of-Scope) 전까지 단일 언어로 고정.
- **검증 방법(권고, 5~6단계 인계)**: 자동 검사(axe-core/Lighthouse Accessibility) + 키보드 전용 수동 통과 + 스크린리더(NVDA 또는 VoiceOver) 스팟 체크를 WU-04(공개 화면) 단위테스트/통합테스트 단계에서 최소 1회 수행할 것을 권고한다(구체적 도구 채택은 06단계 재량).

## 6. 반응형/디바이스 대응 기준

- **브레이크포인트**: `sm` <768px(모바일, 1열 카드), `md` 768~1023px(태블릿, 2열 카드), `lg` 1024~1439px(데스크톱, 2~3열 카드 + 읽기 컬럼 720px 고정), `xl` 1440px+(여백만 확장, 콘텐츠 폭 고정).
- **내비게이션**: `sm`에서는 햄버거 메뉴(카테고리 목록을 드로어로 전환), `md` 이상에서는 상시 노출 가로 내비. 드로어 열림 시 포커스는 드로어 첫 항목으로 이동, 닫힐 때 트리거 버튼으로 복귀(포커스 관리, WCAG 2.4.3).
- **이미지**: Wagtail `CustomRendition`(03 §3.1 ERD에 이미 정의된 다중 렌디션 엔티티)을 활용해 `srcset`으로 화면 폭별 이미지 크기 제공 — 모바일에 불필요하게 큰 원본 이미지를 내려받지 않도록 한다(콜드스타트/저사양 회선 대응과도 연결).
- **폼**: 뉴스레터 구독 폼은 모바일에서 입력창 100% 너비, 버튼은 입력창 아래로 줄바꿈(가로 폭이 좁을 때 버튼이 잘리지 않도록).
- **텍스트 크기 조정**: `rem` 단위 사용으로 브라우저 기본 폰트 크기 조정(200%까지) 시 레이아웃 깨짐 없이 리플로우(WCAG 1.4.4/1.4.10).

## 부록 — 03단계로 회신을 권고하는 후속 항목 (블로킹 아님)

아래는 v1 진행을 막지 않지만, 향후 규칙 F 재작업 시 검토를 권고하는 항목이다(질문 목록 아님 — 모두 현재 설계로 완결 가능한 가역적 사안).

1. `LegalPage`에 콘텐츠 정책 전용 4번째 서브타입/라우트를 별도로 두고 싶다면 03 §3.2/§4 갱신 필요(현재는 `/terms/` 서브섹션으로 충분히 커버됨).
2. 운영자가 콜드스타트 안내 문구를 어드민에서 직접 수정하고 싶다면 03 §3.1 `SiteSettings`에 텍스트 필드 추가 필요(현재는 템플릿 하드코딩으로 충분).
3. StreamField 이미지 블록의 alt 필드는 5단계(WU-02) 구현 명세에 명시적으로 포함할 것(§5, §7).
